# Security and privacy

Agent Trail is an alpha. Security fixes focus on the latest source revision; no older release line has a separate support commitment.

## Report a vulnerability

Report privately through [GitHub private vulnerability reporting](https://github.com/NotYaz/agent-trail/security/advisories/new). Include the affected version or commit, a minimal reproduction with synthetic records, and the impact. Do not include live tokens, private conversations, or complete histories. Agent Trail has one maintainer: fixes land on `main` and ship in the next alpha, and there is no response-time guarantee.

For an ordinary parsing or compatibility bug, use the issue template with redacted examples. See [CONTRIBUTING.md](CONTRIBUTING.md) for fixture guidance.

## Data boundaries

The app reads configured local histories on the Mac: Claude desktop session indexes and JSONL transcripts (a transcript Desktop does not list is opened to read the entrypoint and folder of its opening records, kept in memory, and counted only for `claude` started in a terminal), Codex rollout JSONL under the profile home (default `~/.codex`), Grok `summary.json` plus `updates.jsonl` (default `~/.grok`), Copilot CLI `session-state/<id>/events.jsonl` and `workspace.yaml`'s `cwd` (default `~/.copilot`), and VS Code's Copilot Chat records under the profile's VS Code user-data folder (default `~/Library/Application Support/Code`): each window's `workspace.json`, `chatSessions/<id>.jsonl` (or `.json`) and `chatEditingSessions/<id>/state.json`. When a window opened a multi-root workspace, it also reads that `.code-workspace` file (up to 1 MB, its `folders` only), wherever it was saved. It never reads VS Code's `state.vscdb` databases. It also reads OpenCode's `opencode.db` (and `opencode-<channel>.db`) in its data folder (default `~/.local/share/opencode`), or the database file a profile names, opened with SQLite read-only and `query_only`, never immutable and never copied; queries extract session ids, folders, times, tool names, states, and file paths inside SQLite, so prompts, tool input, output, and diffs are never loaded. It reads Cursor CLI `chats/<hash>/<id>/meta.json` (folder and times only; never `store.db`), and the Cursor app's chat database `User/globalStorage/state.vscdb` under the profile's Cursor data folder, plus each `User/workspaceStorage/<id>/workspace.json` and, for chats from before Cursor 3.0, that folder's `state.vscdb`, and the `.code-workspace` file a chat's workspace names (up to 1 MB, its `folders` only). Cursor's databases are opened with `SQLITE_OPEN_READONLY` and `PRAGMA query_only`, never copied and never opened `immutable`. Each query is a key lookup or key range, except the `composerHeaders` table of chat headers, which has no key range and is read in full. Every query has a time limit and size limits, and records are reduced inside SQLite with `json_extract` to ids, statuses, times, paths, success flags, and value lengths, so prompts, chat titles, code, and file contents are not returned to Agent Trail. A database in WAL mode is opened only while its `-wal` and `-shm` files exist: a read-only SQLite connection maps the existing `-shm` file, as any reader of a WAL database does, and would create one without it. A database with a rollback journal (Cursor 2.x) creates no file when read, so it is read whether or not Cursor is open, but never within 5 seconds of a change to it or its `-journal` file. A reader of such a database holds up Cursor's writes while a query runs, and Cursor gives up on a write after 1 second, so each query stops after 200 milliseconds, looks up at most 8 keys, and fails before loading any value over 8 MB. A busy or stopped query ends that database's scan until the next refresh; nothing is marked unreadable. It reads Gemini CLI `tmp/<project>/chats/session-*.jsonl` (or `.json`) and subagent files under the profile's `.gemini` folder (default `~/.gemini`) and its sibling `.cache/.gemini`, plus each project folder's `.project_root` and `projects.json`, whose paths are trusted only when their SHA-256 matches a session's `projectHash`; and Qwen Code `projects/<project>/chats/<id>.jsonl` and `subagents/<id>/agent-<id>.jsonl` under the profile's runtime folder (default `~/.qwen`). It never reads Gemini or Qwen settings, credentials, `logs.json`, shell history, checkpoints, or file-history backups, and nothing inside a Qwen or Gemini session's working folder. To offer a profile for an assistant found on the Mac, it checks fixed folders for the presence of session files. It does not decompress Codex `.jsonl.zst` archives or treat other assistants' databases as edit evidence. It writes its own settings and incremental activity caches under `~/Library/Application Support/AgentTrail/`. Claude uses `activity-cache.json`. Codex, Grok, Copilot, OpenCode, and Cursor use `activity-cache-codex.json`, `activity-cache-grok.json`, `activity-cache-copilot.json`, `activity-cache-opencode.json`, `activity-cache-cursor.json`, `activity-cache-gemini.json`, and `activity-cache-qwen.json`. It does not change assistant records, install hooks, send telemetry, or upload histories. After a user click, a press of the session switcher's shortcut, or an `agenttrail://` link, it opens a session link (Claude's `claude://code/continue`, Codex's `codex://threads/<id>`) or brings an already running app forward. When several instances of that app run, it reads the parent process IDs of the session's ancestors to pick the instance the session runs under. Link ids are validated before use, and links go only to a running app. With several Claude instances it sends the link only when the session's own instance is the one macOS delivers links to (in testing, the instance launched first). Otherwise it brings the session's own instance forward and shows a hint instead, and it does the same if the open reports a different instance. The app does not launch, quit, kill, or restart assistants, and it uses no Automation or Accessibility permission. The switcher's shortcut is registered through Carbon's `RegisterEventHotKey`, which needs no Accessibility or Input Monitoring permission and delivers only that chord, never other keystrokes. Any app or web page can ask macOS to open an `agenttrail://` link (browsers ask first). Agent Trail accepts only four link forms: values are length- and character-checked, and a link can only select among the live sessions it already shows. A link cannot name a file, an app, or a command. At most it does what that session's Jump button does: it sends the session's link to its running app, brings a running app forward, or shows the session's folder in your running editor or in Finder. Links are never logged. Live session titles, Claude's needs-action sentence, and pull request links are read from local records for display only: they stay in memory and are never cached, exported, or logged.

Live reads Claude process-registry records: Desktop records matched to desktop sessions, and records of `claude` started in a terminal (entrypoint `cli`, interactive, not a spare or parked process), which report their own folder. For a terminal session whose process start is verified, it reads that process's launch record once and keeps only `TERM_PROGRAM` and `__CFBundleIdentifier`, which name the hosting terminal. It also reads Codex app-server writer-handle presence and read-only turn metadata; Grok active-session registry plus explicit lifecycle events matched to the exact PID start; and Copilot CLI `inuse.<pid>.lock` files, counted only while that process is alive and started before the lock, with lifecycle events written after it; for a verified Copilot CLI process it reads `TERM_PROGRAM` and `__CFBundleIdentifier` once, as for Grok; and OpenCode's `~/.local/state/opencode/service.json`, of which only the process ID is read (the password in the same file is never kept, logged, or cached), counted only while that process is alive and started before the file was written, with session execution times, the names, states, and start times of the current step's tool calls (never their input or output), whether that step ended aborted, and the type and reason of each executing session's newest logged execution event read from `opencode.db`; while a session is executing, it also lists the user's `opencode` and `opencode-cli` processes and reads their arguments to find other OpenCode servers, keeping only their process IDs and start times, in memory; and Qwen Code's session registry (`sessions/<pid>.json` under the Qwen home), counting a record only while its process is alive and started no later than the record's `startedAt`, and skipping records written in another PID namespace or on another machine (those with a `pidNs` or `procStart`). Only the PID, session id, folder, start time, and kind are used; the record's `ipcToken` and `ipcPath` are never kept, logged, or used, and the inbox socket is never opened. Registry presence alone yields an Unknown state, never Working, Idle, or Needs input. These readers do not signal or modify assistants. Registry fields, database rows, paths, and process IDs are untrusted input. Omit dead/reused processes and Desktop sessions that cannot be matched. Cursor live status lists this user's running `Cursor` app processes whose parent is launchd (process ID, start time, executable path and `--user-data-dir` from their arguments, kept in memory; their environment is never parsed). It finds the start of the last line of each chat transcript under `~/.cursor/projects/*/agent-transcripts/` by reading backwards from the end, so a prompt can pass through memory, compares only that line's first 32 bytes, and parses or keeps nothing else. Once per chat in a turn, it reads the chat's folder from `composerHeaders` or `composerData` in `state.vscdb`, reduced inside SQLite under the history reader's rules. A recent edit, a leftover lock file, or registry presence alone must not create a live-status claim.

Each cache retains confirmed tool IDs with edit dates and workspace paths, plus file positions and related indexing metadata. They support daily statistics, computed in memory on local activity days, and deduplicate replayed/cross-file results. The Codex and Grok caches, and the Claude cache for terminal sessions, also keep the parent folders of edited files; the Copilot cache keeps each local chat's request and tool ids and times, the file paths its edit tool calls and Undo or Keep events name (whether or not VS Code applied them), the files VS Code applied or the user rejected per request, the parent folders of files the Copilot CLI edited, and the target path of a CLI edit call awaiting its result; the OpenCode cache keeps session ids and parent ids, session folders, times, call ids, and the working folder and parent folders of each counted edit; the Cursor cache keeps chat, message and tool ids, their times, a hash of each chat's listing and the byte length of its record, the folders each chat was placed in, and the paths of edited files; the Gemini CLI and Qwen Code caches keep tool call ids, their times, and the parent folders of edited files, and the Claude cache can briefly keep the target path of an Edit or Write awaiting its result. They do not retain prompts, commands, patches, diffs, or conversation text. Unknown or unreadable cache versions are rebuilt.

The Map reads one project's Git history, and only while the panel's Map tab is showing or the Map window is visible (a covered or minimized window does not count). It reads reflogs as files: `logs/HEAD` in the repository's Git directory and in each linked worktree's administrative folder that still exists, plus the `HEAD` files that name each worktree's branch and the `gitdir` files that name each linked worktree's folder; when the project's `.git` is a file rather than a folder, it also reads that file and the `commondir` file in the Git directory it names. The identity on each reflog line is skipped. Commits and refs come from a Git executable found at the developer directory `/var/db/xcode_select_link` names, the Command Line Tools, `/Applications/Xcode.app`, `/opt/homebrew/bin/git`, or `/usr/local/bin/git`; `/usr/bin/git` is never run, because without the developer tools that stub asks to install them. Each build runs three read-only commands: `for-each-ref` over `refs/heads`, `refs/remotes`, and `refs/tags`; `log --all --reflog` for at most 4,000 commits from a day before the range or the project's first session or cloud commit, whichever is later; and `log --all --reflog --fixed-strings --grep` for the oldest `Claude-Session` trailer. Every command runs with `--no-optional-locks` and `-c core.fsmonitor=false`, `-c log.showSignature=false`, `-c protocol.allow=never`, and `-c core.hooksPath=/dev/null`, in an environment of only `HOME`, `PATH=/usr/bin:/bin`, `LC_ALL=C`, `GIT_TERMINAL_PROMPT=0`, `GIT_OPTIONAL_LOCKS=0`, `GIT_NO_LAZY_FETCH=1`, `GIT_ALLOW_PROTOCOL=none`, and `GIT_NO_REPLACE_OBJECTS=1`, with standard input from `/dev/null` and standard error discarded. A command still running after 10 seconds (3 for the trailer search) is terminated and its output ignored. Git still reads its usual configuration files; the `-c` values take precedence over them. Without such an executable, branch names come from the ref files and `packed-refs`, and no commits are read. From commits the Map keeps hashes, parents, trees, committer dates, subjects, `Co-Authored-By` names without addresses, and a `Claude-Session` value only as the session ID of a `https://claude.ai/code/session_…` link. The committer name is compared with `GitHub` and not kept. Author names and the author's and committer's e-mail addresses are not requested, and the address in each `Co-Authored-By` trailer is dropped when the trailer is parsed. From the Claude Desktop session records it already reads, the Map uses each session's `writtenBranches`, the folder and branch pairs Desktop recorded. Map data stays in memory: the app never caches it or writes it to disk, and it never writes to the repository. `AgentTrailInspect --map` prints a snapshot only when run. A cloud session's claude.ai page opens in the browser only after a click on **Open**, or on **Open session** in a commit's details.

Local paths, profile names, tool IDs, and timestamps can reveal private information. An indexing cache or diagnostic report is not automatically safe to publish. Session logs can contain prompts, source code, commands, credentials, and other secrets. Never attach complete real logs to a public issue.

## Live-status limits

Claude Needs input, Working, and Idle map from explicit `waiting`, `busy`, and `idle` reports; `shell`, a finished turn whose command still runs, shows Working in background. They do not prove actual file activity or completion. Claude writes reports on status changes rather than a guaranteed heartbeat. A recognized report may remain valid for the same verified running process despite its age. Without verified process-start identity, the fallback requires a report no older than 90 seconds. Unsupported flags, implausibly future-dated reports, and stale fallback reports are Unknown. Report age stays visible to the user; CPU usage, file modification times, and saved history do not establish live status.

Claude Needs input requires an explicit `waiting` report, which can represent an input request, approval, or another dialog/request needing attention. It does not always imply a typed answer. Idle means reported idle/ready for the next prompt, not proof of an unanswered request; elapsed inactivity must not create an input request. Live status does not use question, approval, or request text to classify a session.

Codex Working means a loaded thread has an explicit in-progress turn; completed/interrupted/failed turns are Idle. Codex input dialogs cannot currently be distinguished. Grok Working and Idle follow lifecycle events; unresolved explicit permission requests become Needs input. Copilot CLI Working means an open turn or tool call after the session's lock was made; an unanswered permission request or open `ask_user`/`exit_plan_mode` call is Needs input; Copilot Chat in VS Code, Cursor CLI sessions, and Gemini CLI have no live status, and Qwen Code sessions are always Unknown because its registry holds no state. OpenCode Working means a session is executing in a verified service since that service started and no other OpenCode server on the same database that started before the turn is running (while one is, the turn is Unknown, and once it is gone, a turn seen while it ran is not shown); a running `question` call is Needs input, and so is an `edit`, `write`, `patch`, or `read` call still running after 5 seconds: approval prompts are not on disk, and OpenCode stores a call waiting for one like a running call, but these calls otherwise finish in well under a second (a slow code formatter, which OpenCode runs inside the first three, can also hold one). A session waiting to approve a shell command or a subagent stays Working. A turn whose newest step ended aborted (a denied approval or a dismissed question) is not shown, since OpenCode leaves it marked as executing until the next prompt. Cursor Working means a chat's transcript ends with your message, written since a running Cursor app for the profile's data folder started; Cursor writes `turn_ended` when a turn ends, including after Stop, and a Cursor chat is never Needs input. Missing or unsupported lifecycle evidence is Unknown. Live cursors stay in memory; request text is not persisted.

Project cards combine history and reported live sessions without treating one as evidence for the other. A missing live report is not Idle. A project present only in live reports must not gain invented edit/session history. Mixed needs-input/working/idle/unknown counts remain separate, including by profile.

Project cards and expanded live details can show private project/workspace paths, profile names, process IDs, and report times. Use sample mode for public images; do not publish real registry records or unredacted project screenshots.

## Activity images

Growth visualizes available local records; its charts are not Git ancestry and its counts do not measure code quality, lines of code, or productivity. Edit counts come from confirmed file edits on local activity days, which start at 05:00 in the Mac's time zone: Claude `Edit`/`Write`, Codex completed `FileChange`, and Grok completed `write`/`search_replace`. Sessions are grouped by the day they started. The hour-of-day rhythm is shown in the app only. Missing logs, shell commands, and external changes can leave the history incomplete.

PNG export saves only to a user-selected local location and never posts or uploads a card. Project and profile names are hidden by default and can be included with a toggle; folder paths and the hour-of-day rhythm are never included. Totals, dates, and day patterns in the mini calendar remain visible. Review an image before sharing it.

`--demo`, `--render-demo`, `--render-growth-demo`, and `--render-share-demo` use synthetic sample data rather than reading local assistant history or process-registry records. The older `--render-live-demo` flag is an alias for the combined Projects preview. Use these modes for public screenshots. Screenshots of the ordinary app may contain private project names and paths. Demo mode has no Map data. `--render-map` draws a snapshot saved by `AgentTrailInspect --map`, which holds a real project's paths, profile names and folders, session IDs, branch names, commit subjects, and co-author names; treat snapshots and Map renders like diagnostic output.

## Input and distribution

The alpha uses private on-disk formats. Treat records and process information as untrusted input. Unknown data must not result in guessed authorship or arbitrary application activation. Distributed alpha bundles are ad-hoc signed, without Developer ID signing or Apple notarization.
